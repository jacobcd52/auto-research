# Feedback: "How much does the provider matter? Safety evals on one model across every OpenRouter endpoint, against a self-hosted reference"

Reviewer verdict: **major overhaul**. The measurement is feasible and within budget, but the proposal misses the closest prior work (a live, public, per-endpoint-vs-self-hosted-reference index for exactly this model), its headline monitor metric is underpowered on the chosen dataset, and the most likely outcome is an unexciting near-null whose non-null parts are already published.

What I checked (2026-11-14): the parent post and its comments (LessWrong GraphQL), nostalgebraist's post, the OpenRouter endpoints API, Hugging Face (dataset downloaded and inspected; model metadata), arXiv API, RunPod pricing page, Artificial Analysis provider page, OpenRouter Auto Exacto docs. **Not checked:** general web search was unavailable (tool budget exhausted), so the "already done?" search covers only arXiv keyword queries, LessWrong post titles since 2026-07-20, and the two vendor pages; GitHub (including the parent author's coordination-issues repo) was not reachable.

## 1. Would it get upvoted?

Probably 25-60 karma as written; >50 only if it finds a real safety-metric discrepancy with a diagnosed cause, which I put at roughly 25%.

- The parent post got 116 karma for a warning plus one dramatic anecdote. A measurement post has an audience (control/monitoring researchers using gpt-oss-120b as a trusted monitor; Tim Hua-style readers who want measurements, not Claude audits). That audience is real but small.
- The proposal's novelty claim is weaker than stated. **Artificial Analysis launched an "Endpoint Accuracy Index" on 2026-08-04**; the parent post's author flagged it himself in a comment on 2026-10-09. For gpt-oss-120b (high) it already publishes 16 provider endpoints against a self-hosted reference (SGLang 0.5.13 on 8x B200, native MXFP4, launch args disclosed), with 95% CIs, on BFCL-500, HLE-250 and a long-context eval, last run 2026-10-08 to 10-22. The proposal does not mention it. OpenRouter also now publishes its own per-endpoint benchmark numbers on the model's Performance tab and says it is building logprob verification and a "verified provider" tier (parent post update of 2026-07-28).
- What that index shows predicts this project's result. 11 of 16 endpoints "match" the reference. Every "below" endpoint has a mundane diagnosed cause: output caps (DeepInfra Turbo 16k, Groq 65k), tool-call schema/format handling (Groq, Together, Google Vertex), fewer reasoning tokens (Vertex); only Cerebras is unexplained and small (91.8%, CI 84.9-98.7). Nothing resembles R1-on-Targon token soup. The proposal's evals use no tools and short outputs, so the two biggest known causes mostly will not fire.
- So the honest pitch is narrower: "the capability index exists; do safety metrics (monitor scores, threshold calibration) track it or diverge?" Khoriaty's October comment asks exactly this, citing "Accuracy is Not All You Need". That is a legitimate question, but "they track it" is the likely answer and earns maybe 30-45 karma as an all-clear.
- A null on gpt-oss-120b also does not "correct an over-update": the scary anecdote was a 671B reasoning model on a small provider in 2025, and a clean result on a natively-4-bit OpenAI model that every provider serves in the same format does not generalise to DeepSeek/Kimi/GLM/Qwen, where the worry lives.

## 2. Naturalness

Mainline in spirit: the parent post explicitly asks for measured replications, and Tim Hua's criticism was the lack of measurement. But the post's literal request is to **re-run affected published results**, which the proposer rejected (NOTES idea K) and deferred to stage 2. A breadth sweep on a fresh eval battery is the generic version, and the generic version is now what Artificial Analysis and OpenRouter do continuously with more resources. A one-off 2-day snapshot goes stale; a commercial dashboard does not.

Has someone done it? Not for monitor/refusal/legibility metrics that I could find (arXiv queries on OpenRouter/provider variance/refusal returned only Model Equality Testing; no LessWrong post since July besides the parent). The capability half and the "against a self-hosted reference" framing are done (see above). Search coverage was limited as noted.

Model choice works against the question. gpt-oss-120b ships in MXFP4, so quantisation - the mechanism the parent post worries about most - is nearly absent: there is no cheaper format to cut to. The labels are noise: endpoints labelled bf16/fp8/fp16 for a model whose released weights are 4-bit cannot be taken literally, so "does labelled quantisation predict deviation" is ill-posed here. (My count of today's labels: fp4 x11, fp8 x3, bf16 x3, int4 x1, fp16 x1, unknown x7; the proposal says 13/2/3/1/1/6.)

## 3. Pre-mortem

Forecast:

| Outcome | Probability |
|---|---|
| Clear positive: at least one endpoint off-reference on a safety metric beyond noise, cause diagnosed, not just an output cap | 20-25% |
| Clear, defensible negative (all-clear with tight CIs) | 25% |
| Mush: a few "significant" deviations that trace to reasoning-effort/template handling, truncation or under-powered thresholds; arguable either way | 40% |
| Fails to run / reference not trustworthy in time | 10-15% |

Specific problems, most important first.

1. **The monitor eval cannot support the threshold-transfer headline.** I downloaded `abhayesian/basharena-monitor-eval`: 373 rows = 200 honest + 173 attack actions from only 134 trajectories (100 honest, 38 attack). A 2% FPR threshold is set by the 4th-highest of 200 honest scores. Applied elsewhere, observed FPR has a binomial 95% interval of roughly 0.5%-5% from sampling alone, before clustering within trajectories and before score ties (LLM 0-100 scores pile up on multiples of 5). The example success line "2% calibrated on A yields 0.5%-9% elsewhere" is what pure noise looks like at this n. Three samples per action reduce model noise, not item noise.
2. **Attack labels look trajectory-level, not action-level.** The `original_monitor_score` for attack rows has median 6.7 and 75th percentile 35 on a 0-100 scale: most "attack" actions are innocuous steps of an attack trajectory. Action-level AUROC will be mediocre for every endpoint, compressing between-endpoint differences. The dataset has no card, no monitor prompt, 33 downloads and no honest-side original scores, so there is no published number to validate the harness against. It is not "ready-made".
3. **Refusal eval will sit at ceiling.** gpt-oss models refuse plain harmful requests almost always; a 100-prompt no-jailbreak StrongREJECT-style set will give ~97-100% everywhere and detect nothing. (I did not measure this; it is my expectation from the model's reputation, so pilot 20 prompts first.)
4. **"Same request" is the whole result, and it is under-specified.** gpt-oss reasoning effort is a line in the Harmony system message; providers map the `reasoning` parameter differently, and the 2025 AIME 37-93% spread was largely this. The vLLM reference must render the identical prompt. Expect the largest "provider effects" to be reasoning-effort and template differences, which readers will file under "known, see Artificial Analysis", and a 2-day agent team may misattribute its own reference misconfiguration to providers. This is the subtle-eval-bug risk the programme warns about, and it lands on the reference - the one arm everything is compared to.
5. **Noise-band reference is fragile.** A second backend "Transformers" for the 120b needs MXFP4 kernel support; without it Transformers dequantises to bf16 (~230 GB) and will not fit one H100. Use SGLang or llama.cpp instead, or run the second backend only on 20b. Hugging Face metadata confirms 114.7B U8 + 2.2B BF16 params; the repo is 196 GB with all formats, so download only the needed files.
6. **Logprob fingerprint is heavier and leakier than described.** Scoring every provider's text under the reference is ~4M tokens x 52 endpoint-days of teacher-forced forward passes; it also only works if the provider returns reasoning verbatim and the Harmony rendering is exact. It measures "text is typical of the reference", which catches soup but not mild shifts. Only 11 of 26 endpoints advertise `logprobs`, so the cheaper direct comparison (provider top-logprobs vs reference) covers under half.
7. **26 endpoints is about 21 providers.** BaseTen, Parasail and Amazon Bedrock each appear twice; Google showed 0% recent uptime and Venice 75% when I queried; DigitalOcean (4,096) and SiliconFlow (8,192) cap output. Several endpoints will fail `require_parameters:true` for some parameter and drop out, which is itself a finding but shrinks the table.
8. **Schedule.** "Every endpoint twice, 24+ hours apart" in a ~48-hour project means the day-1 sweep must complete, harness debugged and reference validated, within the first ~20 hours. Any harness bug found on day 2 invalidates the day-1/day-2 comparison. Rate limits on small providers at ~17M input tokens per sweep are likely.
9. **GPQA is gated** (`Idavidrein/gpqa`: gated "auto"), so it needs a Hugging Face token with terms accepted - check the team has one, or use the copy the paper's code fetches. Also the paper used GPQA with answer choices removed and a gpt-4o correctness grader; the proposal uses multiple choice, so legibility numbers will not be comparable to the paper's. gpt-oss CoT is plain English and short; the legibility arm will show ~1-2 everywhere and is dead weight.

Claims that checked out: nostalgebraist's numbers (2.28 vs 4.305; 0% vs 20.3% >=7; 40.5% vs 36.6% correct; Jozdien's concession); the parent post's quoted call for replications and Tim Hua's 66-karma comment; arXiv 2605.19537 (16.6 points, 4B-30B) and 2410.20247 (11/31); 26 / 11 / 9 endpoints; price ranges ($0.03-0.35 in, $0.075-0.95 out); max-token range 4,096-117,964; haiku-5.5 $0.10/$0.50, gpt-4o-mini $0.15/$0.60, gpt-4o $2.50/$10; RunPod H100 PCIe $2.89/h and A6000 $0.69/h; gpt-oss-120b and 20b ungated; the monitor dataset is public with 373 rows.

## 4. Cost check

Roughly right in total, wrong in composition. My estimate: **$350-450**, inside the cap.

- Monitor input is under-counted. The dataset is 19.2M characters per pass (~5.5M tokens); x3 samples is ~16.5M input tokens per endpoint per sweep, not 7M total. At an average ~$0.09/M in and ~$0.45/M out with ~4M output: about $3.30 per endpoint-sweep, **~$170** for 52 sweeps (proposal: $130). Worst endpoints (~$0.25-0.35 in) cost ~$7-9 per sweep.
- Grading at "~250M tokens" is over-counted if the legibility arm is cut; with it, ~150M tokens of haiku-5.5 is ~$20.
- GPU: 14 h of H100 is tight if the full logprob-scoring pass is kept (~200M teacher-forced tokens) and a second backend is debugged. Budget 20-25 h (~$60-70) or subsample the scoring.
- Dropping the Llama stretch (gated weights, no reference, $40) and the 20b arm buys back the difference.

## 5. Recommended changes

1. **Cite and build on the Artificial Analysis Endpoint Accuracy Index and OpenRouter's Performance tab.** Reframe the question as: "the capability indices exist; do safety-relevant metrics agree with them?" Report the rank correlation between index score and each safety-metric deviation. Use AA's disclosed reference configuration as a cross-check for the self-hosted reference.
2. **Make the stage-2 item the stage-1 core: re-run one published, provider-sensitive safety result on best and worst endpoints.** This is what the parent post asked for and is the only version with a >50-karma ceiling ("conclusion X flips / does not flip"). Candidates: a BashArena or Control Tower monitor result that used gpt-oss-120b unpinned, with safety/usefulness numbers published. Choose endpoints using the AA index (2 "matches", the 2-3 "below", plus reference), so 5-6 endpoints at depth rather than 26 shallowly.
3. **Fix the monitor eval's power or drop TPR@2%FPR and threshold transfer.** Need thousands of honest actions for a 2% tail: pull honest trajectories from `anonymouslinuxarena/linuxarena-public` from the start, not as a fallback. Use trajectory-clustered bootstrap. Primary metric should be paired: per-action score difference versus reference on identical inputs (mean shift, score-distribution distance), which has far more power than AUROC differences. Pre-register the equivalence margin that would count as "indistinguishable".
4. **Add a model where quantisation and deployment actually vary.** gpt-oss-120b alone cannot test the mechanism. With the 5-6-endpoint design there is budget for one conventionally-quantised model with a single-GPU reference, e.g. a ~30B model in bf16 on an H100, or use `deepseek/deepseek-v3.2` (6 endpoints, fp8/fp4/unknown) without a reference and compare endpoints to each other with a model-equality test. State clearly that results do not transfer to models not tested.
5. **Cut the dead arms.** Drop the CoT legibility grader (gpt-oss will be legible everywhere), the Llama stretch and the price/quantisation-label regressions. Replace the refusal set with borderline prompts piloted to give 30-70% refusal on the reference, or drop it.
6. **Validate the reference before spending on the sweep.** Gate: reference GPQA accuracy and reasoning-token counts must match at least two AA-"matches" endpoints within noise at the same reasoning effort; if not, the bug is assumed to be in the reference. Replace the Transformers second backend with SGLang or llama.cpp.
7. **Collapse the repeat design.** Two sweeps 24 h apart on all endpoints is the main schedule risk; do the drift repeat on the 5-6 focus endpoints only, and same-day duplicate runs for sampling noise.
8. If changes 1-3 are not adopted, **fund proposals 01 or 03 from this cluster ahead of this one**: as written it most likely produces a competent table that restates a vendor dashboard.
